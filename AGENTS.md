# Repository Guidelines

## Project Overview

Dashboard + automation for **bulk registration of Dropbox accounts** (account farming via referral links). A Node.js server exposes a web dashboard and drives a **camofox-browser** REST server (anti-detect Camoufox) that is vendored inside this project; exit IPs rotate through **warp-go** (rootless Cloudflare WARP, SOCKS5), **Psiphon**, or a user-supplied SOCKS5. After the signup form is filled, the vendored **Dropbox daemon** links the new device and triggers the verification email.

Two run modes, same engine:
- **Dashboard**: `node server.js` → `http://localhost:3000` (batch orchestration, live console, progress ring, settings, selector editor, engine status/rotation controls).
- **Interactive CLI**: `node register.js` (prompts for referral URL + `;`-separated emails; `--proxy=true`, `--init=true` flags).

All UI text, log messages, and comments are **Bahasa Indonesia**; identifiers are English-ish camelCase. Branch: `webui3` (remote `https://github.com/Dewamade/Dropbox`).

**x86_64 Linux only.** The vendored Dropbox and Psiphon binaries are x86_64-only; `setup.sh` exits early on any other platform. No Playwright, no system browser, no `warp-ctl`, no Docker, no box64: every executed binary lives in this project directory.

## Architecture & Data Flow

Four-layer backend; the whole frontend is one file.

```
public/index.html (vanilla JS, 1 file: REST + WebSocket client, tabs: Progress / Pengaturan / Selector)
        │  REST /api/*                        │ WS JSON  {action:'start'|'stop'|'ping'}
        ▼                                     ▼
server.js ── Express 5 + ws: batch loop over emails, phase (exit-IP) rotation, worker
        │      state machine, console.* hijack → WS broadcast, live preview screenshots
        ▼
register.js ─ registerSingleEmail(): one camofox *session* per email (userId-keyed
        │      profile), selector-driven form fill, dropboxd in a fresh docker
        │      container + cli_link linking
        ├── camofox-manager.js  spawns/limits ./camofox-browser/server.js (exit path is
        │                       fixed at process start → spec change restarts it)
        ├── camofox-client.js   REST client for one session (tabs, evaluate, click/type)
        └── proxy-manager.js    warp-go + psiphon-tunnel-core lifecycle, SOCKS exit-IP
                                preflight, rotation (new WARP key / new Psiphon region)
db.js ── JSON-file persistence (history.json: registrations + settings + selectors)
```

Data flow per run: UI sends `action:'start'` with the full config → `server.js` builds the email list (`emailMode:'auto'` generates `first.last<2digits>@<domain>` from syllable names, else splits `emails` on `;`) → for each email it builds an ordered phase list from enabled toggles (`direct` → `warp` → `psiphon` → `socks5`; at least one phase is always forced) → inside a phase, `runBrowserLoop` retries up to `globalRetry` times → first success ends the email; total failure for an email **stops the whole batch** and goes idle → every result is written by `saveRegistration()` and mirrored to the UI via WS events.

Per-email exit path (`register.js: ensureExitPath`) → `proxy-manager.startWarp/startPsiphon` (with `rotate` on retry) → `camofox-manager.ensureRunning({proxy, visible})` restarts the browser server if the requested exit/visibility differs → in-browser preflight opens `api.ipify.org` and logs the real exit IP + UA before any account is spent.

Cross-module coupling is via Node `global` (not parameters): `global.safeSend`, `global.killAllVpnProxy`, `global.closeBrowserSession`, `global.killDropboxDaemon`, `global.isDropboxRunning`, `global.previewScreenshot`, `global.livePreview`, `global.currentUserId`, `global.camofoxTab`, `global.warpRotateNext`, `global.psiphonRegions` / `psiphonUsedRegions`, `global.debugProxy`, `global.activeWs`. Preserve this bridge when refactoring.

Worker state machine (`server.js`): `BOOT` → `PROCESSING` → `FINISH` → `IDLE`, driven by a configurable idle timer (`idleTimeout`, default 600 s) that emits `idle_warning` 60 s early; `POST /api/worker-stat/extend|idle` reset or force it, and only from `BOOT`/`FINISH`.

Server→client WS `type`s: `status`, `sync_state`, `worker_status`, `progress`, `log`, `email_success`, `email_stats`, `preview`, `idle_warning`, `idle_warning_cancel`, `pong`. Client→server messages use `action`, not `type`.

## Development Commands

```bash
./setup.sh                                  # installs EVERYTHING into this directory:
                                            # npm deps, camofox-browser (+ Camoufox into
                                            # .camoufox/, + our camofox-plugins/ enabled in
                                            # its camofox.config.json), warp-go (clones +
                                            # builds; Go is auto-downloaded to .toolchain/
                                            # if missing), psiphon binary, dropbox daemon,
                                            # apt packages
./warp/warp -reg                            # one-time WARP registration → warp/reg.json
node server.js                              # dashboard on :3000 (override with PORT=)
node register.js --proxy=false --init=false # CLI mode
```

There is no build step, no bundler, no transpiler for our code: `public/` is served statically, JS is CommonJS. `camofox-browser/` is installed with `npm install --omit=dev` — its dev dependency `openclaw` refuses Node < 24.16 and would abort the install; the REST server needs no dev deps.

## Code Conventions & Common Patterns

- **Module style**: CommonJS (`require`/`module.exports`), `"type":"commonjs"`. One concern per root file; `register.js` self-runs via `if (require.main === module)`.
- **No formatter/linter/tsconfig** — match the surrounding file (4-space indent, semicolons, single quotes). Do not introduce tooling.
- **Never hardcode DOM selectors inline.** Every interaction goes through the selector catalogue: `getSelectors('email_field' | 'continue_button' | 'first_name' | 'last_name' | 'password' | 'tos_checkbox' | 'submit_button' | 'captcha' | 'verify_email' | 'send_email' | 'resend_email' | 'cli_login_email' | 'cli_login_password' | 'cliLink')` — each key is an **array**; an empty result means the in-code fallback list is used — then the tolerant helpers `cf.findVisible(list)` / `cf.waitForVisible(list, ms)` / `cf.clickVisible(list)` / `cf.typeVisible(list, text)`, which try each entry in order. Most-specific → most-generic; that ordering *is* the recovery strategy when Dropbox changes markup. `selector.json` still carries object-shaped legacy keys from the Playwright engine (`register`, `settings`, `verifyEmail`, `accountSetup`, `finalPage`); nothing reads them.
  - camofox `/click` and `/type` accept Playwright selectors (`css`, `:has-text("…")`, `xpath=`) but **one selector at a time**, and the server has no visibility endpoint. So visibility checks go through `camofox-client.findVisible()`: one in-page script walks the catalogue, keeps visible elements, picks the smallest (never an enclosing container), and marks it with `data-cfx="1"`; the click/type then targets that unique node.
  - The catalogue language understood by that script (documented in its own header): plain CSS, `xpath=…`, `scope:has-text("text")`, and **`:xtext("a|b|c")`** — match any of several texts, case- and accent-insensitive, against the element's text *plus* `aria-label`/`title`/`placeholder`/`alt`/`value`. Text after a pseudo-selector is ordinary CSS, so an anchor + descendant works: `.email-block:has-text("mail") button`. Use `:xtext` instead of duplicating catalogue entries per wording.
  - Catalogue seed: `selector.json` (tracked, but overwritten at runtime by `PUT /api/selectors`, which writes both `history.json` and `selector.json`). `register.js` caches it in-process → restart the server after editing on disk. `POST /api/selectors/reset` restores it.
- **camofox session model**: one `userId` per email (`dropbox-<localpart>-<random>`). `POST /tabs` **requires `sessionKey`** in camofox-browser ≥1.17 (it is only a tab-group label; we pass the `userId`). `DELETE /sessions/:userId` destroys tabs and drops the persisted profile dir — that is how a fresh account gets a fresh identity.
- **Daemon linking has three non-obvious rules** (`linkDaemonAndVerifyEmail`): (1) *one device identity per account* — `startDropboxDaemon(tag)` starts a **throwaway container** per account: `docker run -i --rm --init --name dropbox-link-<tag>-<hex3> --net=host --hostname pc-<hex3> -v ./dropbox-app/.dropbox-dist:/opt/dropbox/.dropbox-dist:ro --tmpfs /root/.dropbox --tmpfs /root/Dropbox ubuntu:24.04 sh -c 'printf … > /etc/machine-id; cp /etc/machine-id /var/lib/dbus/machine-id; exec …/dropboxd'`. A never-before-seen container IS a new machine, so the `cli_link_nonce` URL always prints; a *linked* host_id never prints it again, which is why the old host-binary path had to delete `.dropbox/`+`Dropbox/` first. With no docker daemon the same function falls back to running `dropboxd` directly and deletes those two dirs for the same effect (`dropboxMode` = `'docker' | 'native'`, reported by `daemonStatus()` → `/api/proxy/status`); (2) *the nonce is not single-use* — the daemon keeps reprinting the **same** `cli_link_nonce` while unlinked, so a retry re-opens the same URL rather than waiting for a new one (the retry reuses the running container, it does not restart it); (3) *the cli_link page can be Dropbox's login form* (the tab's session dropped, e.g. the exit IP changed mid-flow; proof: `data/debug_error_cli_confirm_*.png` showing "Masuk" + an Email field instead of the Connect button) — `ensureDropboxLogin()` detects that by an email field being visible, re-authenticates with the account's email + password (`cli_login_email` / `cli_login_password`), and only then looks for the Connect button. Failures save `data/debug_error_cli[_confirm]_<localpart>.png` and log the page's visible text. `killDropboxDaemon()` does `docker kill` + `docker rm -f` on the container, SIGTERMs the `docker run` child, then `pkill -9 -f .dropbox-dist` — that one pattern matches both the native daemon (its launcher exec()s into `dropbox-lnx.x86_64-<ver>/dropbox`) and our `docker run` argv, which contains the mount path. `--net=host` means the daemon talks to Dropbox over the host's direct route: the browser's exit IP (WARP/Psiphon) is **not** the daemon's exit, and that is fine — linking is a device action, not a signup.
- **Failure signaling is string-matched across the module boundary** — treat these as a contract:
  - `throw new Error('BROWSER_KILL_REQUIRED: …')` → `server.js` strips the prefix, restarts the browser/tunnels as needed, retries or moves to the next phase.
  - `throw new Error('NO_URL_CHANGE')` → soft failure inside the step loop: reload the tab and retry the step (`maxTabAttempts`) before escalating.
  - `checkTooManyAttempts()` throws `'BROWSER_KILL_REQUIRED: Too many attempts…'` → `server.js` `break`s the phase loop immediately to rotate the exit IP.
  - `throw new Error('DEVICE_CONNECT_FAILED: …')` → thrown by `registerSingleEmail()` **only** when the account already exists and the failure was inside the device-connect step (`linkDaemonAndVerifyEmail`). The contract is: do NOT kill the session. `server.js` calls `global.retryDeviceConnect({ abortController })`, which repeats the device step on the **same** `CamofoxClient`/tab — the account is already created and the tab is already logged in, so this is the only retry that never costs a re-signup or a login. `retryDeviceConnect` owns the session afterwards: it returns `{ success, status: 'success'|'VERIF', password, ip, ua }` and closes the session itself when the step ends.
- **Session lifecycle** — the camofox session (tab + `sha256(userId)` profile) is killed only at: step completion, `Hentikan` (WS stop), or an error that really means "start over" (`BROWSER_KILL_REQUIRED`, total phase failure). `register.js` keeps the live handle in `liveRun` (set right before the device step, cleared by `closeBrowserSession()`); the `finally` of `registerSingleEmail` deliberately skips `closeBrowserSession()` when `keepSessionAlive` is set. Never add a `closeBrowserSession()`/profile wipe to a device-connect failure path: the wipe is what makes the next attempt show Dropbox's login form ("Masuk") instead of the Connect button.
- **Return shape**: `registerSingleEmail()` resolves `{ success, status, password, ip, ua }` where `status` is `'success'` (verification email confirmed) or `'VERIF'` (account created, unverified). `VERIF` is a success in `history.json` but counted separately (`verifCount`) in the UI. A failed **device connect** no longer resolves as `VERIF` — it throws `DEVICE_CONNECT_FAILED` (session kept); the `VERIF` result comes from `retryDeviceConnect()` instead.
- **Timeout units are seconds everywhere** — UI inputs, `db.js` defaults, `server.js` fallbacks, and `selector.json`'s `defaults`. `registerSingleEmail` converts: `const gtMs = globalTimeout * 1000`. Typical values: `globalTimeout` 30–90, `daemonTimeout` 120.
- **Exit paths are keyed by fixed loopback ports**, not config: `warp` → `socks5://127.0.0.1:40000` (`./warp/warp -l 127.0.0.1:40000`), `psiphon` → `socks5://127.0.0.1:3080` (generated from `psiphon.config`), `socks5` → user host. Because camofox pins its proxy at process start (`PROXY_HOST`/`PROXY_PORT` env), `camofox-manager` compares a `specKey` of `[proxy, visible, port]` and restarts the browser server whenever the requested exit changes — the browser is *not* restarted per email.
- **IP rotation semantics**: WARP rotation deletes `warp/reg.json`, runs `./warp/warp -reg` (a new device key ⇒ a different Cloudflare egress), then relaunches with `-l`; the old key is kept as `reg.json.<ts>.bak`. Psiphon rotation restarts the tunnel and picks an unused `EgressRegion` from `global.psiphonRegions` (tracking `global.psiphonUsedRegions`). `register.js` passes `rotate: isRetry || global.warpRotateNext`; the UI exposes both as 🔄 buttons on `POST /api/proxy/rotate` (409 while a batch is running, because rotating would pull the proxy out from under the open tab).
- **Exit-IP proof is one shared endpoint list** — `proxy-manager.EXIT_IP_ENDPOINTS` (`cdn-cgi/trace` → `api.ipify.org` → `ifconfig.me`), each `{ url, parse(text) → {ip, warp?} | null }`. `startWarp()` walks it *through the SOCKS tunnel* (3 rounds) before declaring WARP healthy, and the log line `[Warp] ✓ WARP aktif — exit IP … (warp=on)` is the proof the traffic really left via WARP (the `warp=` flag comes from `cdn-cgi/trace`). `register.js`'s preflight re-reads the same list **inside the browser tab** (tab created on `EXIT_IP_ENDPOINTS[0].url`, later endpoints via `cf.navigate`), because camofox — not the proxy manager — is what must have the proxy applied. Never hardcode a bare ipify call: for a WARP egress range Cloudflare often answers a challenge page (HTML), which parses to nothing and once killed a perfectly working tunnel. A page that yields no IP is a failure to report, never a value to store.
- **WARP logging is deliberately terse** (`proxy-manager`): the log console gets exactly one line per established tunnel (`[Warp] ✓ WARP aktif — exit IP … (warp=on)`) plus errors. Start/stop/tunnel-reuse/rotation progress lines print nothing (`stopWarp()` has no `log` flag). warp-go's own stdout/stderr (it is chatty and writes to **stderr**, in Chinese) never reaches the console: `warpRaw()` keeps the last `WARP_TAIL_MAX = 12` lines in `warpTail` and forwards to `vpnLog` (the `debugProxy`-gated `vpn_log` WS channel), and `dumpWarpTail(reason)` prints them once **only when a start fails** — that is what turns "Port SOCKS5 tidak terbuka" into the real cause (observed: `SOCKS5 监听失败：listen tcp 127.0.0.1:40001: bind: address already in use`). The `exit` handler keys on `warpState.active`, which `stopWarp()` clears *before* killing, so an intentional stop never looks like a crash. Do not add per-step WARP progress lines back.
- **Anti-detection is delegated to Camoufox** — no `userAgent` override, no UA pools, no persistent Firefox profile, no `navigator.webdriver` patches in our code. Keep `useHeadless`/visible handling and the per-userId profile isolation instead.
- **Visible mode** (`useHeadless:false`, UI "Tampilkan Browser"): `camofox-manager` starts the server with `ENABLE_VNC=1`, `VNC_PORT=5902`, `NOVNC_PORT=6082` (camofox VNC plugin); a human solves CAPTHA at `http://localhost:6082`. It also clears `LD_LIBRARY_PATH` for the child: a CUDA `libOpenCL.so.1` earlier on the loader path kills Camoufox renderers right after tab creation (upstream `start-clean.sh` does the same).
- **Screen size is pinned at the X/Camoufox level, never emulated** (`camofox-plugins/screen`). `camofox-manager` exports `SCREEN_RESOLUTION=1360x768` (and `VNC_RESOLUTION` in visible mode); the plugin sets the Xvfb `-screen` argument *and* rewrites the `window.*`/`screen.*` numbers inside the `CAMOU_CONFIG_*` environment chunks that camoufox-js hands to its patched Firefox (that is the only thing that sizes the real window). Verified: Xvfb `1360x768x24`, `screen.width/availWidth` 1360x768, page `innerWidth x innerHeight` = **1360x712** (the window is 1360x768; ~56 px is Firefox UI). Do not reach for the two things that look right and do not work here: Playwright `viewport` (camofox creates contexts with `viewport: null`, and setting one fails — `Browser.setDefaultViewport` sends `isMobile`, which the Firefox driver rejects) and camofox's `POST /tabs/:id/viewport` (Chromium-only, HTTP 500 on Camoufox). When the vnc plugin is on (`ENABLE_VNC=1`) it owns the display and this plugin only follows `VNC_RESOLUTION`; registering a second virtual-display provider would abort the server.
- **The page language is forced, never hoped for** (`camofox-plugins/locale`). dropbox.com serves its UI from the browser's language (`Accept-Language`/`navigator.language`, both derived from Camoufox's `locale:*` config), so a session can come back as Bahasa Indonesia — "Verifikasikan" instead of "Verify email", "Lanjutkan" on the cli_link login — and every text-based selector in the catalogue misses. `camofox-manager` exports `BROWSER_LOCALE=en-US`; the plugin rewrites the `CAMOU_CONFIG_*` chunks with `locale:language`/`locale:region`/`locale:all`, so the whole flow (signup, cli_link page the daemon prints, /account) is English on any exit IP. Two dead ends: `options.locale` inside a plugin is **too late** (camofox builds CAMOU_CONFIG in `buildLaunchOptionsWithGeoipFallback()` before emitting `browser:launching`, exactly why the screen plugin rewrites the env too), and URL tricks (`?lang=en`, `/en/` prefixes) do not cover the `cli_link_nonce` URL, which the daemon generates. `BROWSER_LOCALE=off` disables the lock. The catalogue keeps `:xtext("verify email|verifikasikan|…")` entries as the recovery layer if a page still localizes.
- **Logging**: prefix log lines with a bracketed subsystem tag (`[Warp]`, `[Psiphon]`, `[dropboxd]`, `[Camofox]`, `[Langkah N]`, `[Worker]`, `[Kill]`, `[Selector]`) — the UI colors them. `server.js` hijacks `console.log/error/warn` and forwards JSON-serialized args to the WS, so **never pass an `Error` object as a log argument** (it serializes to `{}`); interpolate `error.message`. Use `global.safeSend({ type:'preview'|…, … })` for non-text streams.
- **Naming**: `camelCase` functions/locals; `UPPER_CASE` for path/port constants (`DROPBOX_DAEMON`, `DAEMON_HOME`, `PSIPHON_BIN`, `WARP_BIN`, `WARP_REG`, `DATA_DIR`); `<snake_case>` keys in `selector.json`; `temp_*.js` = scratch copies kept for diffing against the live file (`temp_register_webui2.js`, `temp_register_1160a43.js` — the old Playwright engine) — nothing imports them.
- **Settings contract** (`db.js` defaults ⇄ `POST /api/settings/apply` ⇄ UI): `aliasWorker`, `urlDropbox`, `emailSource`, `domainEmail`, `count`, `passwordMode`, `fixedPassword`, `globalTimeout`, `globalRetry`, `daemonTimeout`, `useHeadless`, `socks5Host`, `warpPort`, `useDirect`, `useWarp`, `useSocks5`, `usePsiphon`, `psiphonRegions`, `idleTimeout`, `debugProxy`. UA-related fields (`uaMode`, `deviceTypes`) were removed with Playwright.

## Runtime/Tooling Preferences

- **Node.js + npm only**; `package-lock.json` is the lockfile. Runtime deps: `express` 5, `ws`, `socks-proxy-agent`. `playwright`, `@playwright/test`, `proxifly`, `top-user-agents` are gone — do not re-add them.
- **Ports in use** (all hardcoded in the manager modules): 3000 dashboard, **9379** camofox REST (deliberately not 9377/9378 so it cannot collide with an existing camofox instance), 40000 WARP SOCKS5, 3080 Psiphon SOCKS, 5902 VNC / 6082 noVNC.
- **Binaries are installed only by `setup.sh`** and executed only from inside this directory: `camofox-browser/` (git + `camoufox-js fetch`), `warp/warp` (git + `go build`), `psiphon/psiphon-tunnel-core-x86_64` (GitHub raw), `dropbox-app/.dropbox-dist/dropboxd` (dropbox.com tarball). System tools used at runtime: `git`, `curl`/`wget`, `tar`, `pkill`, and optionally `go`. **One exception: the docker engine** — a system service that cannot live in this folder — is the normal host for the Dropbox daemon (the *binary* it runs is still `dropbox-app/.dropbox-dist/dropboxd`, bind-mounted read-only). No docker ⇒ native fallback, never a daemon from elsewhere. `daemonStatus()` reports which mode is live; `GET /api/proxy/status` exposes it as `daemon: {mode, image, imagePresent, running, container}`.
- **System packages** needed to actually run Camoufox / visible mode (printed by `setup.sh` step 8, auto-installed when run as root): Firefox libs (`libgtk-3-0 libdbus-glib-1-2 libxt6 libasound2 libx11-xcb1 libxcomposite1 libxcursor1 libxdamage1 libxfixes3 libxi6 libxrandr2 libxrender1 libxss1 libxtst6 libegl1 libgl1-mesa-dri libgbm1 xvfb`), `x11vnc novnc websockify`, fonts, `docker.io` (daemon container; `setup.sh` also pulls `ubuntu:24.04`), and `build-essential python3` so `better-sqlite3` compiles.
- Gitignored runtime state — a fresh clone starts from defaults; never commit results: `node_modules/`, `.toolchain/`, `camofox-browser/`, `camofox-data/`, `warp/`, `psiphon/`, `dropbox-app/`, `data/`, `history.json`, `selector.json`, `.agents`. In container mode nothing daemon-shaped is ever written under `dropbox-app/` (state is tmpfs inside the container); `dropbox-app/.dropbox/` + `dropbox-app/Dropbox/` only appear in the no-docker fallback.

## Testing & QA

- `npm test` is the npm placeholder (`exit 1`); **no test files exist**. Do not claim coverage; do not add a suite unless asked.
- Verify changes by exercising the real path, cheapest first:
  1. `curl -s localhost:3000/api/proxy/status` → `camofox.installed/browserInstalled` true, `warp.registered`, current exit IPs, and `daemon.mode` = `docker` with `daemon.imagePresent` true (`native` + a printed hint only when no docker engine is running). Same data is in the dashboard under **Pengaturan → Status Mesin Lokal**.
  2. Dashboard Progress tab: **2 emails** from `test.txt` (its referral URLs are the canonical test inputs), `Direct` **or** `Warp+Socks5`, `globalRetry: 1`, headless on. The console must show `[Camofox] ✓ Server siap di http://127.0.0.1:9379` → (WARP only) `[Warp] ✓ WARP aktif — exit IP … (warp=on)` → `[Server] Public IP (via browser/…)` → `[Langkah 1..3]` → `[dropboxd] Perangkat baru via Docker (ubuntu:24.04, hostname pc-…, machine-id …)` (fallback path prints `[dropboxd] State lama dihapus (.dropbox/) …` instead) → `[dropboxd] ✓ URL CLI Link ditemukan` → `[dropboxd] … This computer is now linked to Dropbox` → `✓ Pendaftaran success for <email>`, twice. Both records must be `success` in `history.json` — the second account is the regression check for the device-state reset (a linked host_id makes the daemon silent, which shows up as `[dropboxd] Timeout … URL cli_link tidak muncul` + `VERIF`). `VERIF` from a missing verify-email button is acceptable; a missing `cli_link_nonce` URL is not.
  3. Screen size + language: `node -e` with `require('./camofox-manager').ensureRunning({})`, open a tab, evaluate `innerWidth+'x'+innerHeight` → `1360x712`, `screen.width+'x'+screen.height` → `1360x768`, `navigator.language` → `en-US` (with `BROWSER_LOCALE=id-ID` the same evaluate gives `id-ID` **and** dropbox.com renders "Lanjutkan"/"Masuk" — that is the regression check for the locale plugin); `pgrep -af Xvfb` shows our `-screen 0 1360x768x24` (ignore an older Xvfb from another project).
  4. `cat history.json` → new record with the expected `status`, `ip`, `ua`, `timeouts`, `errors`.
  5. Selector/DOM failures: edit in the **Selector tab** (persisted via `PUT /api/selectors`) rather than editing code, then re-run. `register.js` reads the catalogue from `history.json.selectors`, not from `selector.json` — after editing the file on disk, sync it with `node -e "require('./db').resetSelectors()"` or **Reset** in the Selector tab, otherwise the change never runs. Verify-email failures save `data/debug_error_verif_<localpart>.png` (same helper as `debug_error_cli*`), which is the only way to see what that page actually looked like.
  6. Exit-IP changes: press 🔄 WARP / 🔄 Psiphon and confirm the printed `exit=` in the status panel actually changed (WARP rotation is silent apart from the new `[Warp] ✓ WARP aktif — exit IP …` line and the `reg.json.<ts>.bak` it leaves behind; Cloudflare does sometimes hand back the same egress for a fresh key — an unchanged `exit=` after one rotation is not by itself our bug, retry before concluding).
  7. Log verbosity: a successful WARP start→stop cycle prints exactly one line (`[Warp] ✓ WARP aktif — exit IP … (warp=on)`); reuse, stop, and rotation print nothing, and no `[Warp out]`, `[Warp err]`, or `[warp-go …]` line appears unless `debugProxy` is on (those go to the `vpn_log` WS type) or a start actually failed (`[Warp] log warp-go (…)`).
- Interrupt behaviour is part of QA: press **Hentikan** mid-run and confirm no orphans — `pgrep -fa 'camofox-browser/server\.js|\.camoufox/camoufox-bin|Xvfb|x11vnc|novnc|websockify|\.dropbox-dist|psiphon-tunnel-core|warp -l'` returns nothing (note: `dropboxd` exec()s to `.dropbox-dist/dropbox-lnx.x86_64-<ver>/dropbox`, and our `docker run` argv contains the same mount path, so that one pattern covers both paths) — `docker ps --filter name=dropbox-link-` must be empty (`--rm` + `docker kill` remove it) — and the batch halts with `status:'stopped'`.
- Proxy/VPN tiers need a live network: `./warp/warp -reg` must have succeeded once, and "Too many attempts" from Dropbox is expected behaviour, not a bug — phase rotation/`rotate:true` is the intended remedy.
- If Camoufox starts but every page goes blank right after tab creation, suspect `LD_LIBRARY_PATH` (CUDA `libOpenCL.so.1`); `camofox-manager` clears it for the child process.
