# Repository Guidelines

## Project Overview

Dashboard + automation for **bulk registration of Dropbox accounts** (account farming via referral links). A Node.js server exposes a web dashboard and drives a **camofox-browser** REST server (anti-detect Camoufox) that is vendored inside this project; exit IPs rotate through **warp-go** (rootless Cloudflare WARP, SOCKS5), **Psiphon**, or a user-supplied SOCKS5. After the signup form is filled, the vendored **Dropbox daemon** links the new device and triggers the verification email.

Two run modes, same engine:
- **Dashboard**: `node server.js` → `http://localhost:3000` (batch orchestration, live console, progress ring, settings, selector editor, engine status/rotation controls).
- **Interactive CLI**: `node register.js` (prompts for referral URL + `;`-separated emails; `--proxy=true`, `--init=true` flags).

All UI text, log messages, and comments are **Bahasa Indonesia**; identifiers are English-ish camelCase. Branch: `webui4` (remote `https://github.com/Dewamade/Dropbox`); `setup.sh: BRANCH` pins the same name — a deploy that checks out another branch is switched back by step 3, so bump both together.

**x86_64 Linux only.** The vendored Dropbox and Psiphon binaries are x86_64-only; `setup.sh` exits early on any other platform. No Playwright, no system browser, no `warp-ctl`, no Docker, no box64: every executed binary lives in this project directory.

## Architecture & Data Flow

Four-layer backend; the whole frontend is one file.

```
public/index.html (vanilla JS, 1 file: REST + WebSocket client, tabs: Progress / Pengaturan / Selector)
        │  REST /api/*                        │ WS JSON  {action:'start'|'stop'|'ping'}
        ▼                                     ▼
server.js ── Express 5 + ws: batch loop over emails, retry-path budget (Direct
        │      checkbox + one proxy), worker state machine, console.* hijack → WS
        │      broadcast, live preview screenshots
        ▼
register.js ─ registerSingleEmail(): one camofox *session* per email (userId-keyed
        │      profile), selector-driven form fill, dropboxd in a fresh docker
        │      container + cli_link linking
        ├── camofox-manager.js  spawns/limits ./camofox-browser/server.js (exit path is
        │                       fixed at process start → spec change restarts it)
        ├── camofox-client.js   REST client for one session (tabs, evaluate, click/type)
        └── proxy-manager.js    warp-go + psiphon-tunnel-core lifecycle, SOCKS exit-IP
                                preflight, rotation (new WARP key / new Psiphon region)
db.js ── JSON-file persistence (history.json: registrations + settings + selectors)
```

Data flow per run: UI sends `action:'start'` with the full config → `server.js` builds the identity pool (`emailMode:'auto'` generates `first.last<2digits>@<domain>` from syllable names, else splits `emails` on `;`) → **the retry budget is a STREAK, not a per-email allowance**: one loop (`while (accountsDone < wantedAccounts && !shouldStop)`) in which **every iteration is one attempt with a brand-new identity** — `nextIdentity()` hands out the emails from the UI list first (manual mode's list is only a starting pool), then generates fresh `first.last<2digits>@<same domain>` names — with a budget of `maxAttempts = Math.max(1, globalRetry)` **consecutive failed attempts** (`globalRetry: 1` ⇒ one attempt per account; no proxy is started when none is selected). A success (`success` **or** `VERIF`) raises `accountsDone` and **resets the streak to 0**, so the next account starts at attempt 1 again. Which path an attempt takes is chosen by **two independent UI controls**: a `useDirect` checkbox and the `proxyMode` radio (`'none'` = no proxy, `'warp'`, `'psiphon'` — at most one proxy). `pathFor(attemptNo)` = attempt 1 is `direct` **only if** `useDirect` is on **and no path has succeeded yet in this batch**, otherwise (or from attempt 2 on) the selected proxy; `proxyMode:'none'` means every attempt is direct regardless of the checkbox — `normalizeUseDirect()` forces `useDirect:true` there, because no other path exists. So: Direct + proxy = direct first then proxy; proxy only (Direct unchecked) = **every** attempt, from the first, through that proxy, retried until the streak budget is spent; Direct alone = all direct. **A working path is sticky within a batch** (`workingPath`): the path that produced an account is used again for attempt 1 of the next account (`… — melanjutkan jalur yang sudah berhasil` in the `[Jalur keluar]` line, `isContinuedPath()`), because that exit IP is proven and starting over from Direct would just burn an attempt; `isRetry` stays `false` there, so the tunnel is **not** rotated and the same working exit IP is reused. `workingPath` is a local of the `action:'start'` handler — **only a new batch (`Mulai Pendaftaran`) resets it to Direct-first**. `isRetry` stays `attempt > 1`, i.e. the first attempt of a streak never rotates the tunnel even in proxy-only mode. What is new per attempt: identity, camofox profile (`register.js` mints a fresh `userId` per call, old profile dir deleted) and exit IP (`isRetry=true` ⇒ WARP `reg.json` re-registered / a new Psiphon region). Repeating an email is deliberately impossible: `Too many attempts`/CAPTCHA stick to identity + exit IP, so the same address on the same IP would just fail again. Exhausting the streak **stops the whole batch** and goes idle → every attempt is written by `saveRegistration()` **the moment it ends** (see the counter contract below) and mirrored to the UI via WS events. The old multi-toggle set `useWarp`/`useSocks5`/`usePsiphon`/`socks5Host` is gone from the code; `server.js: normalizeProxyMode()` maps those legacy booleans to `proxyMode` when an old `history.json` is loaded, and the UI does the same for old localStorage. `useDirect` is a live field again and keeps its old meaning ("Direct is not used"); absent = `true` = the old always-direct-first behaviour. Log lines name the attempt explicitly: `[Server] Target N akun; maksimum N percobaan berturut-turut tanpa keberhasilan …` followed by the plan (`Percobaan 1 lewat Direct, sisanya lewat WARP; begitu satu akun jadi lewat WARP, akun berikutnya mulai dari jalur itu lagi` / `Semua percobaan lewat WARP (Direct tidak dipilih)` / `Semua percobaan lewat Direct (tidak ada proxy dipilih)` — `pathPlanText()`), `[Jalur keluar] WARP (SOCKS5 127.0.0.1:40000) — percobaan 2 dari 3 (rentetan tanpa keberhasilan)` (with the suffix ` — melanjutkan jalur yang sudah berhasil` when a sticky `workingPath` chose it), `[Mencoba Kembali] Percobaan 2/3 via … — email + nama BARU: …`, `🔄 Batas Dropbox terdeteksi … — lanjut percobaan k+1/N …` vs `🔄 Kegagalan teknis — …`, `🛑 Batas N percobaan berturut-turut tanpa keberhasilan tercapai (percobaan terakhir via …)`, and the end of the batch prints `📊 Ringkasan batch: X dari N akun jadi — … N BLOCKED (batas Dropbox), N ERROR tercatat.` (`runAttempt`/`nextIdentity`/`pathFor`/`pathLabelOf` in `server.js`). `runBrowserLoop`, the `legs` array, `lastPathType` and the old `❌ GAGAL TOTAL […]: …` summary are **gone**: each failure is reported at the moment it happens, together with its exit path. The old ambiguous label `Warp+Socks5` is gone from both server and engine logs.

Per-email exit path (`register.js: ensureExitPath`) → `proxy-manager.startWarp/startPsiphon` (with `rotate` on retry) → `camofox-manager.ensureRunning({proxy, visible})` restarts the browser server if the requested exit/visibility differs → in-browser preflight opens `api.ipify.org` and logs the real exit IP + UA before any account is spent.

Cross-module coupling is via Node `global` (not parameters): `global.safeSend`, `global.killAllVpnProxy`, `global.closeBrowserSession`, `global.killDropboxDaemon`, `global.isDropboxRunning`, `global.previewScreenshot`, `global.livePreview`, `global.currentUserId`, `global.camofoxTab`, `global.currentExitIp`, `global.warpRotateNext`, `global.psiphonRegions` / `psiphonUsedRegions`, `global.debugProxy`, `global.activeWs`. `global.currentExitIp` is the IP the **current attempt** really exits through: `register.js` sets it once the path is measured (`ensureExitPath`'s host-side value, then the in-tab reading, which is authoritative) and `server.js: runAttempt()` clears it at the start of every attempt, so `failAttempt()` can write into the history record the IP that was actually tried — a failed attempt that died before any measurement (proxy down, tab never opened) leaves it empty and the Riwayat prints `-`. It is never a value to store when unmeasured. Preserve this bridge when refactoring.

Worker state machine (`server.js`): `BOOT` → `PROCESSING` → `FINISH` → `IDLE`, driven by a configurable idle timer (`idleTimeout`, default 600 s) that emits `idle_warning` 60 s early; `POST /api/worker-stat/extend|idle` reset or force it, and only from `BOOT`/`FINISH`.

**`FINISH` means "the machine is free", never "the batch was stopped" — and the UI must not read it as such.** `globalState.lastBatchStopped` is set at the end of `runBatch()` from whether the loop ended by target/limit (`false`) or by a stop request (`true`; the `Hentikan` handler sets it immediately so an in-flight attempt's own end cannot overwrite it), and is cleared when a new batch starts. It rides along on **every** `worker_status` payload (`stopped`, and therefore in `sync_state` too, which embeds a `worker_status`), because a page that connects later must show the same word. `public/index.html updateStatus(text, isIdle, stopped)` maps it: `FINISH` + `stopped` renders **TERHENTI** (grey `status-idle`, same class `updateWorkerStatusDisplay` uses when the engine reports idle), otherwise IDLE→`SIAP` (grey), FINISH→`FINISH` (green), BOOT/PROCESSING→`PROSES` (blue). The worker status is the only label there — the old `IDLE` badge above the log panel is gone. What the batch did is a separate widget: `progress` `status` strings (`Target N akun tercapai.` / `Batch dihentikan.` / `Berhenti: N percobaan gagal berturut-turut.`) go to `#progress-detail`. Both widgets take their word from the server, never from what the page remembers: `sync_state` re-runs `updateStatus()` with the server's own `worker.status`/`stopped` (`lastWorkerStatus` is not a source of truth) and `updateProgress()` with `progress.status`/`total`/`successCount`, so a stopped batch cannot come back as FINISH after a refresh.

Server→client WS `type`s: `status`, `sync_state`, `worker_status`, `progress`, `log`, `email_success`, `email_stats`, `preview`, `idle_warning`, `idle_warning_cancel`, `pong`. Client→server messages use `action`, not `type`.

**The progress ring counts finished successes, never attempts.** A `progress` payload carries `current`/`total` (`total` = `wantedAccounts`, fixed for the whole batch; `current` is vestigial — always 0 since attempts no longer map to emails, and the UI never uses it) plus the authoritative `successCount` / `limitCount` / `errorCount` / `verifCount` (`server.js counterFields()`, the four counters are documented above it). `public/index.html updateProgress()` draws `% = (successCount + verifCount) / total`: VERIF counts as finished (it is a success in `history.json`), a failure never moves the ring, and `current` is never the numerator. Payloads do not always carry every counter, so the UI keeps the last known values in `progressCounts` (that is why the end-of-batch payload also sends `verifCount`). Consequently **every branch that changes a counter must send a `progress` event**: `server.js: failAttempt()` writes the record, bumps the counter and pushes `progress` in one place, so the `[FAIL] Blocked (batas Dropbox / CAPTCHA) — percobaan <k>/<N> via <path> → <email>` log line and the Blocked/Error card always move together (`progress.status` names the class: `Gagal Blocked: <email>` / `Gagal Error: <email>`). The end-of-batch `progress` only carries the summary status (`Target N akun tercapai.` / `Batch dihentikan.` / `Berhenti: N percobaan gagal berturut-turut.`) plus `total`; there is no `Gagal total …` payload any more because the class was already announced per attempt. Which class a failed email belongs to is **derived from the last error message**, not from control flow: `server.js LIMIT_ERROR_PATTERN` / `isLimitFailure()` match Dropbox's own wording (`too many attempts`, `please try later`, `captcha`, Indonesian variants) ⇒ LIMIT (the remedy is another exit IP + profile, and in visible mode a human at noVNC); anything else (timeout, dead proxy, missing button, `DEVICE_CONNECT_FAILED`) ⇒ ERROR. That one pattern is the only classifier: the `❌ Error percobaan …` line, the `🔄 Batas Dropbox terdeteksi …` vs `🔄 Kegagalan teknis …` line, the `[FAIL]` line and the `failClass` in the record all read the same `isLimitFailure()` result, so a new failure type is handled by extending the pattern, never by special-casing the batch loop. Pressing **Hentikan** sends **no** `progress` event and does **not** zero the counters — `globalState.progress` keeps its last tally so a page that loads later (`sync_state`) shows the same numbers as the open page; only starting a *new* batch (`server.js: action:'start'`) resets them to 0.

**One history record per attempt; the Riwayat modal is just another view of those counters.** `db.js: saveRegistration()` takes ONE object: `{ email, password, status, alias, ip, connection, attempt, failClass? }` — `status` ∈ `'success' | 'VERIF' | 'failed'`; `connection` is the exit path of *that* attempt (`'direct' | 'warp' | 'psiphon' | 'socks5'`), passed straight from the `proxyType` of the attempt that produced it (`server.js: runAttempt`/`failAttempt`), so a `failed` record always names the path that actually failed — there is no shared `lastPathType` variable any more; `ip` is the **exit IP that attempt was measured at** (`global.currentExitIp`), written for every status including `failed` — that is the only number that says *which* IP Dropbox rejected, and an attempt that died before any measurement stores an empty string; `attempt` is which attempt of the streak it was (1-based, survives a manual-emails restart); `failClass` ∈ `'limit' | 'error'` is written only for `failed`. Nothing else is stored: `ua`, `timeouts`, `errors` are gone from `history.json` — per-attempt timeouts/errors live in the transient `email_stats` card (reset per identity, because every attempt is a new identity), `result.ua` only feeds the live info panel, and the record is the ledger of *attempts*, written at the moment the attempt ends. Consequently `Ringkasan Berdasarkan Alias` has exactly the columns `Alias | Sukses | Blocked | Error`: Sukses = `success` + `VERIF` (the same invariant as the ring), Blocked/Error are the `failClass` counts — the **visible word is "Blocked"** (Dropbox's own blocking: rate-limit/CAPTCHA) while the field/element names stay `limitCount` / `stat-limit-count` / `failClass:'limit'`; there is deliberately no `Gagal`/`Verif`/`Total` column (Gagal = Blocked + Error; Total is derivable and was noise). The detail table's `Status` column is derived, not stored: `public/index.html: historyStatus(r)` reproduces exactly the summary's invariant (`success`/`VERIF` → `Sukses` `badge-sukses`, green; `failed` + `failClass:'limit'` → `Blocked` `badge-limit`, amber; `failed` + `failClass:'error'` → `Error` `badge-error`, red; an old `failed` record without `failClass` → `Blocked` with a `title` saying the class is unknown), because the raw engine words (`success`, `failed`, `VERIF`, and the `BELUM TERKONFIRMASI` badge that came with it) are not the words the live cards use and reading them side by side was the reported bug — "yang jelas itu sukses, blocked, error". Its `IP` cell is the record's own `ip`, so a failure prints the exit IP that was tried (`-` when nothing was measured); the last column is `Koneksi`, labelled by `connectionLabel()`; records written before those fields existed render `-`. `DELETE /api/history` (**Hapus Semua Riwayat**) clears `registrations[]` only — `settings` and `selectors` survive.

## Development Commands

```bash
./setup.sh                                  # installs EVERYTHING into this directory:
                                            # npm deps, camofox-browser (+ Camoufox into
                                            # .camoufox/, + our camofox-plugins/ enabled in
                                            # its camofox.config.json), warp-go (clones +
                                            # builds; Go is auto-downloaded to .toolchain/
                                            # if missing), psiphon binary, dropbox daemon,
                                            # apt packages
./warp/warp -reg                            # one-time WARP registration → warp/reg.json
node server.js                              # dashboard on :3000 (override with PORT=)
node register.js --proxy=false --init=false # CLI mode
```

There is no build step, no bundler, no transpiler for our code: `public/` is served statically, JS is CommonJS. `camofox-browser/` is installed with `npm install --omit=dev` — its dev dependency `openclaw` refuses Node < 24.16 and would abort the install; the REST server needs no dev deps.

## Code Conventions & Common Patterns

- **Module style**: CommonJS (`require`/`module.exports`), `"type":"commonjs"`. One concern per root file; `register.js` self-runs via `if (require.main === module)`.
- **No formatter/linter/tsconfig** — match the surrounding file (4-space indent, semicolons, single quotes). Do not introduce tooling.
- **Never hardcode DOM selectors inline.** Every interaction goes through the selector catalogue: `getSelectors('email_field' | 'continue_button' | 'first_name' | 'last_name' | 'password' | 'tos_checkbox' | 'submit_button' | 'captcha' | 'verify_email' | 'send_email' | 'resend_email' | 'cli_login_email' | 'cli_login_password' | 'cliLink')` — each key is an **array**; an empty result means the in-code fallback list is used — then the tolerant helpers `cf.findVisible(list)` / `cf.waitForVisible(list, ms)` / `cf.clickVisible(list)` / `cf.typeVisible(list, text)`, which try each entry in order. Most-specific → most-generic; that ordering *is* the recovery strategy when Dropbox changes markup. `selector.json` still carries object-shaped legacy keys from the Playwright engine (`register`, `settings`, `verifyEmail`, `accountSetup`, `finalPage`); nothing reads them.
  - camofox `/click` and `/type` accept Playwright selectors (`css`, `:has-text("…")`, `xpath=`) but **one selector at a time**, and the server has no visibility endpoint. So visibility checks go through `camofox-client.findVisible()`: one in-page script walks the catalogue, keeps visible elements, picks the smallest (never an enclosing container), and marks it with `data-cfx="1"`; the click/type then targets that unique node.
  - The catalogue language understood by that script (documented in its own header): plain CSS, `xpath=…`, `scope:has-text("text")`, and **`:xtext("a|b|c")`** — match any of several texts, case- and accent-insensitive, against the element's text *plus* `aria-label`/`title`/`placeholder`/`alt`/`value`. Text after a pseudo-selector is ordinary CSS, so an anchor + descendant works: `.email-block:has-text("mail") button`. Use `:xtext` instead of duplicating catalogue entries per wording.
  - Catalogue seed: `selector.json` (tracked). **`db.js: loadDB()` seeds `history.json.selectors` from that file whenever the catalogue is empty** — first run on a fresh machine, a hand-written `history.json`, or a corrupt one (the corrupt branch seeds in memory only and never overwrites the user's file). Without that seed the first `history.json` contained `"selectors": {}` and every `getSelectors(key)` in `register.js` silently returned `[]` ⇒ the hardcoded in-code fallback lists ran on every step and the catalogue looked empty until someone pressed **Reset**. `PUT /api/selectors` overwrites both `history.json` and `selector.json`; `register.js` caches the catalogue in-process → restart the server after editing on disk. `POST /api/selectors/reset` re-syncs from `selector.json`. The catalogue object has top-level keys `selectors` (the arrays, keyed by `snake_case`) + `defaults`; `register.js: getSelectors()` accepts either the flat or the nested shape.
- **camofox session model**: one `userId` per email (`register.js:410` — `dropbox-<localpart>-<Date.now().base36><4 rand>`, so an id never repeats). **A profile is destroyed, never reused: `DELETE /sessions/:userId` closes the tabs but leaves `camofox-data/profiles/<sha256(userId)[:32]>` on disk** — the `persistence` plugin *writes* `storage-state.json` (cookies + localStorage) on `session:destroying` and on `server:shutdown`, so the dir appears at close time (verified). Two halves keep the next run clean: `camofox-manager.cleanupProfile(userId)` (fs wipe, called only from `register.js: closeBrowserSession()` — reached from every completion path: the `finally` of `registerSingleEmail`, the end of `retryDeviceConnect`, every batch-stop branch in `server.js`, and `shutdown()` on SIGINT/SIGTERM) and `camofox-manager.wipeSessionState()`, called by `ensureRunning()` **before every server spawn**: it deletes the whole contents of `camofox-data/{profiles,cookies,uploads,traces}`, because at that point no session can be alive and anything there belongs to a dead run (SIGKILL, crash, another project). Proven by `tmp-profile-fresh-probe.js`: an unclosed session leaves `storage-state.json` on disk, the next `ensureRunning` clears all four dirs, and reopening with the **same** userId evaluates `document.cookie === ''` and no localStorage.
- **Daemon linking has three non-obvious rules** (`linkDaemonAndVerifyEmail`): (1) *one device identity per account* — `startDropboxDaemon(tag)` starts a **throwaway container** per account: `docker run -i --rm --init --name dropbox-link-<tag>-<hex3> --net=host --hostname pc-<hex3> -v ./dropbox-app/.dropbox-dist:/opt/dropbox/.dropbox-dist:ro --tmpfs /root/.dropbox --tmpfs /root/Dropbox ubuntu:24.04 sh -c 'printf … > /etc/machine-id; cp /etc/machine-id /var/lib/dbus/machine-id; exec …/dropboxd'`. A never-before-seen container IS a new machine, so the `cli_link_nonce` URL always prints; a *linked* host_id never prints it again, which is why the old host-binary path had to delete `.dropbox/`+`Dropbox/` first. With no docker daemon the same function falls back to running `dropboxd` directly and deletes those two dirs for the same effect (`dropboxMode` = `'docker' | 'native'`, reported by `daemonStatus()` → `/api/proxy/status`); (2) *the nonce is not single-use* — the daemon keeps reprinting the **same** `cli_link_nonce` while unlinked, so a retry re-opens the same URL rather than waiting for a new one (the retry reuses the running container, it does not restart it); the **console never repeats it either**: `onDaemon` drops any daemon line that contains a cli_link URL (`CLI_LINK_URL_RE` — the same pattern that captures the URL for `cf.navigate`), so the URL is printed exactly once per run, as `[dropboxd] ✓ URL CLI Link ditemukan: …`, and only when it differs from the one already reported (the daemon's own `This computer isn't linked …` lines still pass through). `linkDaemonAndVerifyEmail()` also does `removeAllListeners('data')` on the daemon's stdout/stderr before attaching its handler, because `retryDeviceConnect()` runs this function a second time on the *same* live process and two handlers would print the line twice; (3) *the cli_link page can be Dropbox's login form* (the tab's session dropped, e.g. the exit IP changed mid-flow; proof: `data/debug_error_cli_confirm_*.png` showing "Masuk" + an Email field instead of the Connect button) — `ensureDropboxLogin()` detects that by an email field being visible, re-authenticates with the account's email + password (`cli_login_email` / `cli_login_password`), and only then looks for the Connect button. Failures save `data/debug_error_cli[_confirm]_<localpart>.png` and log the page's visible text. `killDropboxDaemon()` does `docker kill` + `docker rm -f` on the container, SIGTERMs the `docker run` child, then `pkill -9 -f .dropbox-dist` — that one pattern matches both the native daemon (its launcher exec()s into `dropbox-lnx.x86_64-<ver>/dropbox`) and our `docker run` argv, which contains the mount path. `--net=host` means the daemon talks to Dropbox over the host's direct route: the browser's exit IP (WARP/Psiphon) is **not** the daemon's exit, and that is fine — linking is a device action, not a signup.
- **Failure signaling is string-matched across the module boundary** — treat these as a contract:
  - `throw new Error('BROWSER_KILL_REQUIRED: …')` → `server.js` strips the prefix and restarts the browser/tunnels as needed before the next attempt.
  - `throw new Error('NO_URL_CHANGE')` → soft failure inside the step loop: reload the tab and retry the step (`maxTabAttempts`) before escalating.
  - `checkTooManyAttempts()` throws `'BROWSER_KILL_REQUIRED: Too many attempts…'` → counted as **BLOCKED** (`isLimitFailure()`) and the batch's **streak** counter moves: session reset, then the next attempt gets a brand-new email + name + profile + rotated exit IP (`Percobaan k/maxAttempts`). Only `maxAttempts` *consecutive* failures stop the batch; a success resets the streak (it used to `break` out of the loop early — that spent an email on a single attempt, and repeating an email against a rate-limit never helped anyway).
  - `throw new Error('DEVICE_CONNECT_FAILED: …')` → thrown by `registerSingleEmail()` **only** when the account already exists and the failure was inside the device-connect step (`linkDaemonAndVerifyEmail`). The contract is: do NOT kill the session. `server.js` calls `global.retryDeviceConnect({ abortController })`, which repeats the device step on the **same** `CamofoxClient`/tab — the account is already created and the tab is already logged in, so this is the only retry that never costs a re-signup or a login. `retryDeviceConnect` owns the session afterwards: it returns `{ success, status: 'success'|'VERIF', password, ip, ua }` and closes the session itself when the step ends.
- **Session lifecycle** — the camofox session (tab + `sha256(userId)` profile) is killed only at: step completion, `Hentikan` (WS stop), or an error that really means "start over" (`BROWSER_KILL_REQUIRED`, exhaustion of the attempt budget). `register.js` keeps the live handle in `liveRun` (set right before the device step, cleared by `closeBrowserSession()`); the `finally` of `registerSingleEmail` deliberately skips `closeBrowserSession()` when `keepSessionAlive` is set. Never add a `closeBrowserSession()`/profile wipe to a device-connect failure path: the wipe is what makes the next attempt show Dropbox's login form ("Masuk") instead of the Connect button.
- **Return shape**: `registerSingleEmail()` resolves `{ success, status, password, ip, ua }` where `status` is `'success'` (verification email confirmed) or `'VERIF'` (account created, unverified). `VERIF` is a success in `history.json` but counted separately (`verifCount`) in the UI. A failed **device connect** no longer resolves as `VERIF` — it throws `DEVICE_CONNECT_FAILED` (session kept); the `VERIF` result comes from `retryDeviceConnect()` instead.
- **Timeout units are seconds everywhere** — UI inputs, `db.js` defaults, `server.js` fallbacks, and `selector.json`'s `defaults`. `registerSingleEmail` converts: `const gtMs = globalTimeout * 1000`. Typical values: `globalTimeout` 30–90, `daemonTimeout` 120.
- **Exit paths are keyed by fixed loopback ports**, not config: `warp` → `socks5://127.0.0.1:40000` (`./warp/warp -l 127.0.0.1:40000`), `psiphon` → `socks5://127.0.0.1:3080` (generated from `psiphon.config`), `socks5` → a host passed programmatically. The dashboard only offers `direct`/`warp`/`psiphon` (the free-text SOCKS5 host field was removed); `register.js: ensureExitPath()` still accepts `socks5` for the CLI (`node register.js --proxy=socks5`). Because camofox pins its proxy at process start (`PROXY_HOST`/`PROXY_PORT` env), `camofox-manager` compares a `specKey` of `[proxy, visible, port]` and restarts the browser server whenever the requested exit changes — the browser is *not* restarted per email.
- **IP rotation semantics**: WARP rotation deletes `warp/reg.json`, runs `./warp/warp -reg` (a new device key ⇒ a different Cloudflare egress), then relaunches with `-l`; the old key is kept as `reg.json.<ts>.bak`. Psiphon rotation restarts the tunnel and picks an unused `EgressRegion` from `global.psiphonRegions` (tracking `global.psiphonUsedRegions`). `register.js` passes `rotate: isRetry || global.warpRotateNext`; the UI exposes both as 🔄 buttons on `POST /api/proxy/rotate` (409 while a batch is running, because rotating would pull the proxy out from under the open tab).
- **Exit-IP proof is one shared endpoint list** — `proxy-manager.EXIT_IP_ENDPOINTS` (`cdn-cgi/trace` → `api.ipify.org` → `ifconfig.me`), each `{ url, parse(text) → {ip, warp?} | null }`. `startWarp()` walks it *through the SOCKS tunnel* (3 rounds) before declaring WARP healthy, and the log line `[Warp] ✓ WARP aktif — exit IP … (warp=on)` is the proof the traffic really left via WARP (the `warp=` flag comes from `cdn-cgi/trace`). `register.js`'s preflight re-reads the same list **inside the browser tab** (tab created on `EXIT_IP_ENDPOINTS[0].url`, later endpoints via `cf.navigate`), because camofox — not the proxy manager — is what must have the proxy applied. Never hardcode a bare ipify call: for a WARP egress range Cloudflare often answers a challenge page (HTML), which parses to nothing and once killed a perfectly working tunnel. A page that yields no IP is a failure to report, never a value to store.
- **The exit IP is per-destination, so the console reports the engine's** — this network has two uplinks, so one host answers differently per endpoint (measured 2026-11-20 with `warp=off`, 3/3 stable: `api.ipify.org` and `ifconfig.me` see MoRa `AS131111 / 202.150.68.x`, `www.cloudflare.com/cdn-cgi/trace` sees MyRepublic `AS63859 / 103.156.165.x`). Two different IPs in one console is therefore multi-WAN routing, never a proxy — and `dropbox.com` (Fastly-fronted) sees a third value, which is why only `warp`/`psiphon` really change an account's IP identity. The console line `[Info] Exit IP Camoufox: … (WARP, warp=on, via www.cloudflare.com)` (`public/index.html: logEngineExitIp()`, fired on WebSocket connect/page load and on **Mulai**) therefore asks the **server** (`GET /api/exit-ip`), never the viewer's browser: the path is the live camofox pin (`camofox.status().proxy`, `null` = direct) or, when no engine is up, the configured `proxyMode` path — measured host-side over that same path (`directExitIp` / `socksExitIp`), so no browser is started for one log line. The response carries `ip`/`warp`/`endpoint`/`via`/`exitPath`/`engineRunning` and the UI prints them; an engine this process does not own is labelled "engine belum jalan" (`camofox.isRunning()` is per-process). `register.js`'s in-tab `[Server] Public IP (via browser/<mode>)` and `ip` in `history.json` stay the authoritative measurements; a path that cannot be measured logs "belum bisa diukur", never a stale number.
- **`warp-go` is only usable with `patches/warp-go-dns-http2-init.patch` applied.** `http2.Transport.NewClientConn()` in x/net v0.56 does not run `Transport.init()`, so the internal net/http transport stays nil and warp-go SIGSEGVs inside `dnsQuery()` (process exits with code 2). Only a client that sends a **domain name** triggers it: Camoufox/Firefox on a SOCKS proxy asks the proxy to resolve (`www.cloudflare.com` in the reported stack = the in-tab preflight's `EXIT_IP_ENDPOINTS[0]`), while `proxy-manager.socksExitIp()` uses `socks-proxy-agent`, which resolves on the host and hands warp-go an IP. That asymmetry *is* the symptom: `[Warp] ✓ WARP aktif — exit IP …` prints (the host-side preflight passed) and the tunnel dies the moment the browser opens its first page — every later step then fails as a technical ERROR and rotating WARP changes nothing, because the bug is in the binary, not the exit. Proved 2026-11-21 by building upstream `ca2f0cc` twice: unpatched → panic and no answer through `curl --proxy socks5h://…`; with the patch → answer. Since `warp/` is gitignored, `setup.sh` step 6 applies the tracked patch (idempotent: greps for the patched line, warns instead of failing when upstream has moved on), **rebuilds an already-installed binary whose source is unpatched** — a machine that built warp-go before this patch existed is in exactly that state, and `warp/warp -l` there will keep dying until it is rebuilt — and proves the behaviour for a freshly built binary when `warp/reg.json` exists (probe port 40099, spawned with `cwd: warp/` like `proxy-manager.js:219` because warp-go reads `reg.json` relative to its working directory; log `data/warp-dns-probe.log`; all four branches verified 2026-11-21 in a sandbox copy: unpatched binary → detected + patched + rebuilt + probe OK, already-patched source → "sudah ada", no reg.json → probe skipped). Do not "fix" this by making the browser resolve names locally — keeping the lookup inside the tunnel is also what stops a DNS leak.
- **WARP logging is deliberately terse** (`proxy-manager`): the log console gets exactly one line per established tunnel (`[Warp] ✓ WARP aktif — exit IP … (warp=on)`) plus errors. Start/stop/tunnel-reuse/rotation progress lines print nothing (`stopWarp()` has no `log` flag). warp-go's own stdout/stderr (it is chatty and writes to **stderr**, in Chinese) never reaches the console: `warpRaw()` keeps the last `WARP_TAIL_MAX = 120` lines in `warpTail` and forwards to `vpnLog` (the `debugProxy`-gated `vpn_log` WS channel), and `dumpWarpTail(reason)` prints them once **only when a start fails** — that is what turns "Port SOCKS5 tidak terbuka" into the real cause (observed: `SOCKS5 监听失败：listen tcp 127.0.0.1:40001: bind: address already in use`). A Go panic's cause is its **first** line (`panic: … [signal SIGSEGV]`) with the interesting frames just below it, so the buffer has to survive 20-40 lines and the dump starts at the first `panic:`/`SIGSEGV` it finds (`— mulai dari panic` in the header), capped at `WARP_DUMP_MAX = 45`; the old 12-line ring cut the cause away and left only the bottom of a stack, which cost a debugging session on a remote machine. The `exit` handler keys on `warpState.active`, which `stopWarp()` clears *before* killing, so an intentional stop never looks like a crash. Do not add per-step WARP progress lines back.
- **Anti-detection is delegated to Camoufox** — no `userAgent` override, no UA pools, no persistent Firefox profile, no `navigator.webdriver` patches in our code. Keep `useHeadless`/visible handling and the per-userId profile isolation instead.
- **Visible mode** (`useHeadless:false`, UI "Tampilkan Browser"): `camofox-manager` starts the server with `ENABLE_VNC=1`, `VNC_PORT=5902`, `NOVNC_PORT=6082` (camofox VNC plugin); a human solves CAPTCHA at `novncUrl()` = `http://localhost:6082/vnc.html?autoconnect=true&resize=scale` — that exact URL is what the readiness log prints, what `status().novncUrl` returns, and what the dashboard's noVNC link uses (it only rewrites the hostname, so the dashboard works from another machine too). **Both params are load-bearing:** bare `…/vnc.html` leaves noVNC's Scaling at its HTML default (`off`) and shows a Connect dialog, so the 1360x768 desktop is drawn 1:1 and the bottom/right of the browser window is cut off in any viewer window smaller than that. `resize=scale` (noVNC "Local Scaling") fits the whole desktop into the window — verified by opening it inside a Camoufox tab: the desktop renders as a full Droste mirror, no clipped edge. `resize=remote` is the wrong knob here (it asks the *server* to resize the display, which Xvfb cannot do after start, and it would break the pinned screen). Do not "fix" clipping by lowering `VNC_RESOLUTION`/`SCREEN_RESOLUTION` — the display is correct (`-screen 0 1360x768x24` → x11vnc `-rfbport 5902` → websockify `6082`), and shrinking it changes the window size dropbox.com sees. `camofox-manager` also clears `LD_LIBRARY_PATH` for the child: a CUDA `libOpenCL.so.1` earlier on the loader path kills Camoufox renderers right after tab creation (upstream `start-clean.sh` does the same).
- **Screen size is pinned at the X/Camoufox level, never emulated** (`camofox-plugins/screen`). `camofox-manager` exports `SCREEN_RESOLUTION=1360x768` (and `VNC_RESOLUTION` in visible mode); the plugin sets the Xvfb `-screen` argument *and* rewrites the `window.*`/`screen.*` numbers inside the `CAMOU_CONFIG_*` environment chunks that camoufox-js hands to its patched Firefox (that is the only thing that sizes the real window). Verified: Xvfb `1360x768x24`, `screen.width/availWidth` 1360x768, page `innerWidth x innerHeight` = **1360x712** (the window is 1360x768; ~56 px is Firefox UI). Do not reach for the two things that look right and do not work here: Playwright `viewport` (camofox creates contexts with `viewport: null`, and setting one fails — `Browser.setDefaultViewport` sends `isMobile`, which the Firefox driver rejects) and camofox's `POST /tabs/:id/viewport` (Chromium-only, HTTP 500 on Camoufox). When the vnc plugin is on (`ENABLE_VNC=1`) it owns the display and this plugin only follows `VNC_RESOLUTION`; registering a second virtual-display provider would abort the server.
- **The page language is forced, never hoped for** (`camofox-plugins/locale`). dropbox.com serves its UI from the browser's language (`Accept-Language`/`navigator.language`, both derived from Camoufox's `locale:*` config), so a session can come back as Bahasa Indonesia — "Verifikasikan" instead of "Verify email", "Lanjutkan" on the cli_link login — and every text-based selector in the catalogue misses. `camofox-manager` exports `BROWSER_LOCALE=en-US`; the plugin rewrites the `CAMOU_CONFIG_*` chunks with `locale:language`/`locale:region`/`locale:all`, so the whole flow (signup, cli_link page the daemon prints, /account) is English on any exit IP. Two dead ends: `options.locale` inside a plugin is **too late** (camofox builds CAMOU_CONFIG in `buildLaunchOptionsWithGeoipFallback()` before emitting `browser:launching`, exactly why the screen plugin rewrites the env too), and URL tricks (`?lang=en`, `/en/` prefixes) do not cover the `cli_link_nonce` URL, which the daemon generates. `BROWSER_LOCALE=off` disables the lock. The catalogue keeps `:xtext("verify email|verifikasikan|…")` entries as the recovery layer if a page still localizes.
- **The live preview is a screenshot scaled by CSS, never re-captured.** `server.js` streams `type:'preview'` frames at the pinned page size (1360x712); `public/index.html` puts them in `.preview-scroll` inside `.browser-preview`, and the `#preview-zoom` dropdown (1x–4x) sets `--preview-zoom` on the box — **1x = fit-to-box**, so 2x ≈ native pixels and 3x/4x are browser interpolation; the image overflows and the box scrolls (centered on change and on each new frame). The zoom control lives *outside* the scroll container so it never scrolls away, and is shown only via `:has(img.visible)`. The progress sidebar column is `minmax(300px, min(560px, 34vw))` (`index.css .progress-layout`) so the preview is legible at 1x — widen that, do not shrink the screenshot or the browser screen. The chosen zoom is a browser preference in `localStorage['dropbox_signup_preview_zoom']`; it is deliberately **not** in the settings contract (`db.js` defaults ⇄ `POST /api/settings/apply` ⇄ `history.json.settings`) because nothing in the engine reads it.
- **Logging**: prefix log lines with a bracketed subsystem tag (`[Warp]`, `[Psiphon]`, `[dropboxd]`, `[Camofox]`, `[Langkah N]`, `[Worker]`, `[Kill]`, `[Selector]`, `[FAIL]`, `[stub]` in the QA stub) — the UI colors them. `server.js` hijacks `console.log/error/warn` and forwards JSON-serialized args to the WS, so **never pass an `Error` object as a log argument** (it serializes to `{}`); interpolate `error.message`. Use `global.safeSend({ type:'preview'|…, … })` for non-text streams.
- **Naming**: `camelCase` functions/locals; `UPPER_CASE` for path/port constants (`DROPBOX_DAEMON`, `DAEMON_HOME`, `PSIPHON_BIN`, `WARP_BIN`, `WARP_REG`, `DATA_DIR`); `<snake_case>` keys in `selector.json`; `temp_*.js` = scratch copies kept for diffing against the live file (`temp_register_webui2.js`, `temp_register_1160a43.js` — the old Playwright engine) — nothing imports them; `tmp-stub-loader.js` + `tmp-stub-register.js` = the engine stub used by QA steps 2b–2d and 2g–2h (nothing imports them either; `STUB_NO_IP=<nomor panggilan>` makes those calls resolve without an exit IP, which is how the "no IP measured" failure branch is reproduced without a dead proxy); `tmp-singleproxy-probe.js`, `tmp-counter-probe.js`, `tmp-history-probe.js` (QA 2g — REST/WS only, no browser), `tmp-dashboard-ui-probe.js`, `tmp-path-ui-probe.js` (QA 2f — it also reads and restores the server's proxy settings through REST, so it is safe to re-run), `tmp-riwayat-ui-probe.js` (QA 2h) = the WS/UI probes those steps run — they talk to a server on `PORT=3007` over REST/WS/Camoufox, so they need the stub server up, not the real engine; `tmp-profile-fresh-probe.js` (QA 2e) is the exception: it drives `camofox-manager` + `camofox-client` itself and needs no server.
- **Settings contract** (`db.js` defaults ⇄ `POST /api/settings/apply` ⇄ UI): `aliasWorker`, `urlDropbox`, `emailSource`, `domainEmail`, `count`, `passwordMode`, `fixedPassword`, `globalTimeout`, `globalRetry`, `daemonTimeout`, `useHeadless`, `proxyMode`, `useDirect`, `warpPort`, `psiphonRegions`, `idleTimeout`, `debugProxy`, `enablePreview`. Exit paths are a **pair**: `proxyMode` ∈ `'none' | 'warp' | 'psiphon'` (**one** proxy maximum) and `useDirect` (checkbox) — UI group "Jalur Keluar" = one Direct checkbox + three proxy radios ("Tanpa proxy" / WARP / Psiphon). `server.js: normalizeProxyMode()` + `normalizeUseDirect()` validate the pair at load and on `POST /api/settings/apply`; `normalizeUseDirect()` forces `useDirect:true` whenever `proxyMode === 'none'` (without a proxy there is no other path to run), and `public/index.html: setProxyMode()`/`setUseDirect()`/`updateProxyPathUI()` enforce exactly the same rule in the form (the Direct checkbox is checked-and-disabled when "Tanpa proxy" is selected, and the group prints the resulting plan as a live "Rencana: …" line). `public/index.html: getUseDirect()` is what every payload uses, so the UI can never send a combination the server would reject. `globalRetry` is the **consecutive-failure streak budget** for the whole batch, not a per-email allowance (see Data flow): the batch stops after that many failures in a row, and any success resets it. `count` / the manual `emails` list is the **target account count** (`wantedAccounts`); in manual mode the typed list is only the starting identity pool — once those are used, `nextIdentity()` generates new names on the last used domain. Removed fields: `uaMode`, `deviceTypes` (went with Playwright) and the multi-toggle set `useWarp`/`useSocks5`/`usePsiphon` + `socks5Host` (an old `history.json`/localStorage may still carry them — the two proxy booleans are mapped to `proxyMode`, nothing else reads them). `useDirect` used to be in that list and is **live again with its old meaning** ("Direct is not used"): old `useDirect:false` + `useWarp:true` migrates to today's proxy-only batch, and a missing field means `true` = the previous always-direct-first behaviour. There is nothing left to validate as "pilih setidaknya satu tipe koneksi": `proxyMode:'none'` is a valid direct-only batch, and it is the only case where Direct cannot be turned off.
- **The server, not localStorage, is what the dashboard loads.** `loadSettings()` takes `GET /api/settings` when it answers and only falls back to `localStorage['dropbox_signup_settings']` when it does not — so every field read from the API must be read under its **contract name**. `saveSettings()` writes the UI-side names (`useVisible` = `!useHeadless`, `alias`, `url`, …), which exist only in that fallback; reading `settings.useVisible` from the API response silently leaves the widget at its default (that was the "Tampilkan Browser is not saved after re-running the script" bug). Engine-affecting toggles do not wait for the Apply button: `#use-visible` POSTs a partial `{ useHeadless }` to `/api/settings/apply` on change — apply merges with the stored settings, so half-edited form fields are untouched, and a batch already in flight is unaffected because it captured its own settings from the `action:'start'` payload.

## Runtime/Tooling Preferences

- **Node.js + npm only**; `package-lock.json` is the lockfile. Runtime deps: `express` 5, `ws`, `socks-proxy-agent`. `playwright`, `@playwright/test`, `proxifly`, `top-user-agents` are gone — do not re-add them.
- **Ports in use** (all hardcoded in the manager modules): 3000 dashboard, **9379** camofox REST (deliberately not 9377/9378 so it cannot collide with an existing camofox instance), 40000 WARP SOCKS5, 3080 Psiphon SOCKS, 5902 VNC / 6082 noVNC.
- **Binaries are installed only by `setup.sh`** and executed only from inside this directory: `camofox-browser/` (git + `camoufox-js fetch`), `warp/warp` (git + `go build`), `psiphon/psiphon-tunnel-core-x86_64` (GitHub raw), `dropbox-app/.dropbox-dist/dropboxd` (dropbox.com tarball), `app/cloudflared` (Cloudflare Tunnel, `github.com/cloudflare/cloudflared/releases/latest/download/cloudflared-linux-amd64`; **nothing in this project runs it yet** — it is vendored here so a tunnel never reaches for a binary outside the folder). System tools used at runtime: `git`, `curl`/`wget`, `tar`, `pkill`, and optionally `go`. **One exception: the docker engine** — a system service that cannot live in this folder — is the normal host for the Dropbox daemon (the *binary* it runs is still `dropbox-app/.dropbox-dist/dropboxd`, bind-mounted read-only). No docker ⇒ native fallback, never a daemon from elsewhere. `daemonStatus()` reports which mode is live; `GET /api/proxy/status` exposes it as `daemon: {mode, image, imagePresent, running, container}`.
- **System packages** needed to actually run Camoufox / visible mode (installed by `setup.sh` **step 2**, before any `npm install`, auto-installed when run as root; non-root just prints the list — do not move this step later, `better-sqlite3` is compiled during camofox's `npm install`): Firefox libs (`libgtk-3-0 libdbus-glib-1-2 libxt6 libasound2 libx11-xcb1 libxcomposite1 libxcursor1 libxdamage1 libxfixes3 libxi6 libxrandr2 libxrender1 libxss1 libxtst6 libegl1 libgl1-mesa-dri libgbm1 xvfb`), `x11vnc novnc websockify`, fonts, `git` + `procps` (clone steps, `pkill`), `docker.io` (daemon container; `setup.sh` also pulls `ubuntu:24.04`), and `build-essential python3` so `better-sqlite3` compiles.
- Gitignored runtime state — a fresh clone starts from defaults; never commit results: `node_modules/`, `.toolchain/`, `camofox-browser/`, `camofox-data/`, `dropbox-app/`, `psiphon/`, `warp/`, `app/`, `data/`, `history.json`, `.agents`. **`selector.json` deliberately is NOT in that list** (it used to be listed while also being tracked, which did nothing except mislead — `.gitignore` has no effect on a tracked file): it is the catalogue seed `db.js` copies into a fresh `history.json`, so it must ship; dropping it from git would send every new machine back to the in-code fallback lists. `history.json` is the opposite case: untracked + ignored, so it never ships. In container mode nothing daemon-shaped is ever written under `dropbox-app/` (state is tmpfs inside the container); `dropbox-app/.dropbox/` + `dropbox-app/Dropbox/` only appear in the no-docker fallback.

- Interrupt behaviour is part of QA: press **Hentikan** mid-run and confirm no orphans — `pgrep -fa 'camofox-browser/server\.js|\.camoufox/camoufox-bin|Xvfb|x11vnc|novnc|websockify|\.dropbox-dist|psiphon-tunnel-core|warp -l'` returns nothing (note: `dropboxd` exec()s to `.dropbox-dist/dropbox-lnx.x86_64-<ver>/dropbox`, and our `docker run` argv contains the same mount path, so that one pattern covers both paths) — `docker ps --filter name=dropbox-link-` must be empty (`--rm` + `docker kill` remove it) — and the batch halts with `status:'stopped'`.
- Proxy/VPN tiers need a live network: `./warp/warp -reg` must have succeeded once, and "Too many attempts" from Dropbox is expected behaviour, not a bug — the remedy is the next attempt (new profile + `rotate:true` on the selected path), which is exactly what the `globalRetry` budget spends.
- If Camoufox starts but every page goes blank right after tab creation, suspect `LD_LIBRARY_PATH` (CUDA `libOpenCL.so.1`); `camofox-manager` clears it for the child process.
